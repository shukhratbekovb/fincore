# ADR-001 — Double-entry ledger и синхронная проекция баланса

Статус: реализовано. Обновлено 15 ноября 2026; обязательность double-entry и атомарности задана PRD §6–9.

## Контекст

Перевод должен сохранять деньги при параллельных запросах и сбоях. Одного изменяемого поля balance недостаточно для проверяемой истории. Нельзя публиковать половину проводки.

## Решение

Хранить immutable LedgerTransaction и LedgerEntry в PostgreSQL. Пользовательский счёт — LIABILITY: CREDIT увеличивает баланс, DEBIT уменьшает. Sandbox funding — системный ASSET: DEBIT увеличивает виртуальное фондирование.

WalletBalance хранит posted_minor и обновляется в той же транзакции, что проводки. Available равен posted до появления holds. Денежные значения — положительные BIGINT cents; баланс неотрицателен.

Финансовые use cases создают LedgerTransaction/entries и изменяют проекции в одной UoW под блокировками. Миграции устанавливают constraints, deferred validation и immutable triggers; PostgreSQL проверяет сбалансированную пару и соответствие источнику операции. Отдельная posting function и ограниченные runtime DB roles сейчас не реализованы. Read-only reconciliation сверяет журнал и проекции в одном snapshot.

## Рассмотренные альтернативы

- Только изменяемый balance: недостаточная проверяемость истории.
- Асинхронная проекция: усложняет проверку доступных средств и допускает устаревшие значения.
- Независимые commits списания и зачисления: нарушают требование атомарности.

## Последствия

Чтение баланса быстрое, история проверяема. Возникает обязанность регулярно тестировать reconciliation, права БД и rollback. Исправления проведённых операций требуют новых компенсирующих проводок; API refunds/reversals исключён из MVP. Нельзя «исправить» историю UPDATE/DELETE.

## Подтверждение

ACC-03–06, ACC-09, ACC-11, ACC-14 из [плана тестирования](../test-plan.md); проверки неизменяемости и единственного posting для успешной операции.
