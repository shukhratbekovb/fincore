# Спецификация frontend MVP

Обновлено: 16 октября 2026. Основание: PRD и [согласованное изменение scope](scope-update-2026-10-16.md). Пять разделов и несколько CAD-кошельков согласованы. URL и детали UI ниже — предложения реализации.

## Пользователи и границы

Гость регистрируется и входит. User создаёт несколько CAD wallets, смотрит баланс, переводит виртуальные средства и читает свою историю. Sandbox operator может пополнить тестовый кошелёк только при серверном разрешении и в разрешённом окружении.

Постоянная заметная отметка: «Sandbox · Виртуальные средства». Обычному user не показывать публичное пополнение с карты или self-mint. Не создавать неработающие разделы Cards, FX, Loans, Investments, Refunds или Analytics ради наполнения навигации.

## Карта экранов — разделы согласованы, URL предложены

| Route | Экран | Данные и действия |
|---|---|---|
| `/login` | Вход | Email, пароль, ссылка регистрации |
| `/register` | Регистрация | Email, пароль, правила и ошибки; переход ко входу, если API не выдаёт сессию |
| `/` | Главная | Общий баланс CAD, карточки кошельков, быстрый перевод, последние операции |
| `/wallets` | Кошельки | Карточки всех кошельков, создание с названием и цветом |
| `/wallets/:id` | Выбранный кошелёк | Баланс, статус, ID, копирование, история и перевод |
| `/profile` | Профиль | Данные пользователя, настройки оформления и выход |
| `/transfers/new` | Перевод | Выбор source, другой пользователь или свой wallet, сумма CAD, проверка и подтверждение |
| `/transactions` | История | Все операции, фильтр wallet, тип, направление, сумма, время, cursor pagination |
| `/transfers/:id` | Детали перевода | Статус, сумма, участники в разрешённом объёме, ID, время |
| `/sandbox/top-ups` | Опциональная форма оператора | Wallet UUID, сумма, результат; только по capability |

Навигация: **Главная → Кошельки → Перевод → История → Профиль**. На телефоне — пять пунктов снизу, Перевод по центру; на desktop — боковая панель. Быстрые действия ведут в Перевод с выбранным source wallet. Профиль показывает доступные данные пользователя, оформление и выход; API редактирования профиля пока не определён. Карточки кошельков на главной листаются на телефоне и располагаются сеткой на desktop. Таблица истории адаптируется в список.

## Основные сценарии

### Вход и сессия

Поля имеют подписи и доступные ошибки. Во время отправки повторная отправка блокируется. Сессия загружается до показа защищённых данных. При истечении access token — согласованный refresh; при окончательной потере сессии очистить пользовательские данные и перевести ко входу. После выхода данные предыдущего пользователя не остаются в cache или на экране.

Точная политика пароля и refresh transport остаются открытыми. Не добавлять password reset, email verification или социальный вход: соответствующих flows нет в PRD.

### Создание кошелька

`GET /wallets` с пустым списком показывает onboarding. Пользователь может создать несколько CAD wallets с названием и цветом; поля API и лимит количества уточняются. Каждый новый wallet получает независимый нулевой баланс и account. Второй CAD wallet не является конфликтом. Выбор другой валюты пока отсутствует.

### Перевод

1. Выбрать собственный source wallet из карточек/списка; быстрое действие предвыбирает его.
2. Выбрать сценарий: другому пользователю — destination UUID; между своими — другой собственный wallet. Ввести сумму CAD. Lookup API внешнего получателя отсутствует.
3. Проверить UUID, запрет перевода в тот же wallet, положительную сумму и максимум два десятичных знака. Показать известный баланс, но окончательное решение принимает сервер.
4. Предложение UX: экран/блок проверки с полным ID получателя и суммой.
5. При подтверждении создать idempotency key; отправить целые cents.
6. При COMPLETED показать результат и обновить баланс/историю.
7. При бизнес-отклонении показать понятную причину, сохранив введённые данные.
8. При сетевой неопределённости показать «Не удалось подтвердить результат» и безопасный повтор того же запроса с тем же ключом.

Состояния формы: editing → review → submitting → success / rejected / outcome_unknown. Это UI-состояния; в Transfer API остаются COMPLETED / REJECTED. Повторный клик и повтор доставки не должны создавать новый ключ. См. [ADR-002](adr/ADR-002-idempotency.md).

### История и детали

Общая история требует единой серверной выборки и фильтра wallet. Внутренний перевод показывать одной операцией в общей истории, а в истории каждого wallet — своим направлением. Общий баланс CAD не меняется от внутреннего перевода; правила агрегации статусов и API пока открыты. Wallet transactions включают проведённые движения и top-up; transfer list — бизнес-переводы. Не смешивать отклонённый перевод с проведённым расходом. Для cursor pagination использовать непрозрачный `next_cursor`; null означает конец. Не рассчитывать номера страниц без поддержки API.

Для каждой строки: направление текстом/иконкой, сумма с CAD, тип, дата. Не полагаться только на красный/зелёный цвет. Время API UTC, отображение — в локальном часовом поясе с понятной подписью в деталях. Для перехода от ledger transaction к transfer нужен source ID, отсутствующий в примере ответа PRD; до согласования не строить URL из ledger ID.

### Sandbox top-up

Опциональный экран не является публичной админ-панелью. Условия: capability оператора, разрешённое окружение, server limits и idempotency. При отказе доступа форма недоступна; сам API независимо проверяет разрешение. Операторский токен нельзя встраивать в frontend bundle.

## Матрица состояний

| Состояние | Реакция UI |
|---|---|
| Начальная загрузка | Skeleton/индикатор; не показывать вымышленный нулевой баланс |
| Нет кошелька | Создание CAD wallet |
| Нет операций | Понятное пустое состояние |
| Нулевой баланс | Показать 0.00 CAD; объяснить недостаток средств при попытке перевода |
| Wallet FROZEN/CLOSED | Видимый статус, ограничения действий по принятой политике |
| 401 | Один согласованный refresh, затем login при неуспехе |
| 403/404 | Нет доступа/ресурс недоступен, без раскрытия чужих данных |
| 409 | Различать конфликт payload и конкурентный запрос после уточнения кодов; второй CAD wallet допустим |
| 422 | Недостаток средств/неактивный wallet; не показывать успех |
| 429 | Сообщение об ограничении и retry policy по контракту |
| 503/offline/timeout | Ошибка чтения с retry; для денег — сохранение контекста и проверка результата |

## Деньги и доступность

Не использовать `parseFloat(value) * 100` для построения денежной команды. Разбирать строку с целой и дробной частями, нормализовать разрешённый разделитель и проверять диапазон. Примеры: `100.00` → `10000`, `0.01` → `1`; пустое, ноль, отрицательное, exponent и более двух дробных знаков отклонять. Допустимость запятой — UX-решение; обработка должна быть однозначной. Диапазон BIGINT/JS требует D14.

Предлагаемые критерии: работа клавиатурой, видимый focus, labels, текстовые ошибки рядом с полями, перенос focus к результату, доступное сообщение о копировании. На ширине 320 px не должно быть горизонтального скролла страницы; длинные UUID переносятся или сокращаются с возможностью прочитать/скопировать полностью.

## Готовность frontend

Каждый экран имеет loading/empty/error/success states; реализованы FE-01–15 из [плана проверок](test-plan.md). Mock mode явно обозначен. Финансовые гарантии подтверждает backend на PostgreSQL. Стек принят: Next.js App Router + TypeScript, Tailwind CSS, Lucide, next-themes и Zod. Реализован локальный интерактивный demo в `frontend/`; язык пока русский. Auth/API integration и финансовая correctness требуют отдельной реализации и проверок.
