Transfers funds between distinct wallets in one currency. The JWT actor must own the sender wallet. Both wallets and ledger accounts must allow posting. The operation, two journal entries, both balance projections and replay result commit atomically. Idempotency-Key is required. Identical key/payload replays the original transfer_id with 201; changed payload returns 409. Contention waits up to two seconds before retryable 409 idempotency_in_progress. Rejected attempts roll back without persisted REJECTED operations. The success response is returned after commit.

Requires a Bearer access JWT and an active user. Monetary fields in these new financial responses are decimal minor-unit strings. Request amount_minor accepts a JSON integer or digit string, never bool/float. Currency is explicit. Timestamps are timezone-aware. Responses including expected errors use Cache-Control: no-store. Errors use the shared detail.code/message/errors envelope without SQL details or secrets.

Redis limits transfer creation POST requests: defaults are 30 per minute per JWT user and 100 per minute per IP. The user budget spans all wallets and Idempotency-Key values. Replaying a completed transfer also consumes the HTTP budget and can return 429; retry the same key and payload when the budget becomes available. Idempotency still prevents duplicate debits. Configure TRANSFER_RATE_LIMIT_USER_PER_MINUTE and TRANSFER_RATE_LIMIT_IP_PER_MINUTE. JWT and the required header are validated before consuming a budget; transfer GET endpoints are unaffected by this rule.

Exceeding either budget returns `429` with `Retry-After`. Redis unavailability returns `503 rate_limiter_unavailable` without executing the use case.
