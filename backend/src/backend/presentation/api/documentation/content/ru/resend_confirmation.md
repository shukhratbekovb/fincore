Запрос новой ссылки регистрации: `POST /v1/auth/confirm/resend`.
Публичный эндпоинт принимает только `email`, без Bearer-токена и пароля.
Email нормализуется по тем же правилам, что и при регистрации.

Допущенный запрос с корректным телом получает `202`, включая неизвестные адреса
и уже активные либо недоступные для подтверждения аккаунты. Общий текст ответа
не сообщает, зарегистрирована ли почта. Ответ означает принятие запроса, а не доставку.

Новое письмо создаётся только для пользователя в `pending_confirmation`. Под
блокировкой пользователя все неиспользованные регистрационные challenges помечаются
использованными, сохраняется хеш нового токена и задача outbox в одной транзакции.
Предыдущие ссылки регистрации перестают работать. Подтверждения сброса пароля
не меняются. Срок задаёт `VERIFICATION_CONFIRMATION_TTL`, по умолчанию один час.
Для доставки должен работать отдельный почтовый worker.

```json
{"email":"alice@example.com"}
```

До выполнения use case Redis учитывает попытки: по умолчанию 20 на IP в час
и 3 на нормализованный email в час, включая неизвестные и активные аккаунты.
При превышении возвращается `429` с `Retry-After`; при недоступном Redis —
`503 rate_limiter_unavailable`, операция не выполняется. Отсутствующий IP даёт
`400`, некорректные или лишние поля — `422`. Небольшая минимальная задержка ответа
уменьшает различия времени обработки разных аккаунтов.

Используйте последнюю ссылку и отправьте её токен с выбранным паролем в
`POST /v1/auth/confirm`. Повторный `/register` продолжает возвращать конфликт уникальности.
