FinCore API описывает реализованные HTTP-эндпоинты аутентификации и проверку доступности приложения.
Ссылки **RU / EN** сверху переключают язык документации. Пути, JSON-поля, идентификаторы операций
и коды ошибок одинаковы в обеих версиях. Реальные сообщения об ошибках API остаются на английском языке.

## Быстрый старт

1. Выполните `POST /v1/auth/register` с username и email. Сохраните полученный `user_id`.
2. Получите токен подтверждения регистрации через сценарий доставки.
3. Выполните `POST /v1/auth/confirm` с токеном и новым паролем. При успехе вернётся `204` без тела.
4. Выполните `POST /v1/auth/login` с username и паролем, чтобы получить пару access/refresh-токенов.
5. Обновляйте токены через `POST /v1/auth/refresh`. После каждого успеха сохраняйте заменяющий refresh-токен.
6. Завершайте сессию через `POST /v1/auth/logout`, передав её refresh-токен.

Регистрация создаёт аккаунт в ожидании подтверждения и задание на доставку подтверждения.
Доставку выполняет отдельный outbox worker: локально через SMTP Mailpit, в production через SES SMTP.
`201` означает сохранение задания, а не доставку письма.
Ответ регистрации не раскрывает токен. Вход доступен после подтверждения, установки пароля и активации аккаунта.
Смена пароля доступна через `/v1/auth/change-password`, сброс — через `/v1/auth/password-reset/request` и `/v1/auth/password-reset/confirm`.

## Запросы и примеры

Эндпоинты аутентификации принимают JSON с `Content-Type: application/json`.
Для change-password нужен заголовок `Authorization: Bearer <access_token>`. Остальные эндпоинты не требуют access JWT; подтверждение, refresh и logout используют свой токен в теле.
Успешные тела ответов и ожидаемые ошибки возвращаются в JSON; у ответов `204` тела нет.
Локальные примеры используют `http://127.0.0.1:8000`; в развёрнутом клиенте подставьте свой HTTPS-адрес API.
Аккаунты, UUID и строки токенов в примерах вымышлены. **Токены в примерах условные: это не рабочие JWT или секреты.**

В подтверждении сброса неизвестные JSON-поля запрещены; в остальных запросах они игнорируются. Передача `ip_address` или `user_agent` в JSON не задаёт
метаданные сессии. Для login/refresh сервер использует IP соединения и необязательный заголовок `User-Agent`.
User-Agent — описание, задаваемое клиентом. За Nginx заголовки пересылки должны приниматься только
от настроенного доверенного прокси. Прямой клиент не может выбрать записанный IP через эти заголовки.

## Токены и срок действия

Access-токен — подписанный JWT. Refresh-токен — непрозрачный секрет сессии, а токен подтверждения —
отдельный одноразовый секрет регистрации. Они не взаимозаменяемы. Токены возвращаются в JSON;
текущие эндпоинты не устанавливают cookies авторизации.

Сроки зависят от настроек развёртывания. Значения по умолчанию: **30 минут** для access-токена,
**30 дней** для сессии и **1 час** для подтверждения регистрации. Токен или сессия истекают уже
в момент наступления срока. Refresh сохраняет исходный идентификатор и абсолютный срок сессии.

Для одной сессии выполняйте refresh-запросы последовательно. Повторное использование уже потраченного
refresh-токена отзывает сессию и возвращает `401 invalid_refresh_token`. Поэтому параллельные запросы
могут отозвать сессию после успеха одного из них. После таймаута нельзя безусловно повторять запрос
с тем же токеном: сервер мог его уже использовать. Если результат неизвестен, получите новую сессию через вход.

Logout запрещает дальнейшее обновление токенов этой сессии. Он **не аннулирует автоматически** ранее
выданные access JWT: немедленный отзыв доступа требует отдельной проверки сессии в защищённых эндпоинтах.

## Ошибки

У ожидаемых ошибок единый формат:

```json
{
  "detail": {
    "code": "invalid_credentials",
    "message": "Invalid username or password",
    "errors": []
  }
}
```

Для программной обработки используйте `detail.code` и HTTP-статус. Массив `errors` содержит ошибки
валидации с `loc`, `message` и `type`; исходные значения запроса и контекст валидации не возвращаются.
Непредвиденные сбои остаются `500`: сейчас фреймворк возвращает для них текстовый ответ о серверной ошибке.
Они не являются ошибками валидации и не используют JSON-схему ожидаемых ошибок.

| Код | HTTP | Значение |
| --- | --- | --- |
| `request_validation_error` | 422 | Некорректный JSON, отсутствующие поля, неверные типы, длина или формат |
| `invalid_username`, `invalid_email`, `invalid_password` | 422 | Значение не прошло доменную валидацию |
| `email_already_exists`, `username_already_exists` | 409 | Конфликт регистрации с существующим аккаунтом |
| `invalid_credentials` | 401 | Учётные данные неверны либо пароль ещё не установлен |
| `user_inactive` | 403 | Аккаунт неактивен; при входе проверяется после проверки пароля |
| `invalid_refresh_token` | 401 | Неизвестный, истёкший, отозванный либо повторный refresh-токен или сессия |
| `invalid_confirmation_token` | 400 | Неизвестный токен или другое назначение подтверждения |
| `confirmation_token_expired` | 400 | Срок подтверждения истёк |
| `confirmation_token_used` | 400 | Подтверждение уже использовано |
| `user_not_pending_confirmation` | 409 | Аккаунт больше не ожидает подтверждения |
| `user_not_found` | 404 | Пользователь, связанный с подтверждением, отсутствует |
| `http_error` | Зависит от статуса | HTTP-ошибка, включая невозможность определить IP клиента (`400`) |

Общие обработчики также знают `invalid_access_token` и `access_token_expired` (`401`).
Эти коды используются в защищённом change-password. Для сброса пароля все недействительные reset-токены дают `400 invalid_password_reset_token`. Лимиты сброса возвращают `429 http_error` с заголовком `Retry-After`. Новый пароль возвращается один раз в JSON и не отправляется по email. Все auth-ответы имеют `Cache-Control: no-store`.

## Профиль и сессии

Все `/v1/users/me` операции требуют `Authorization: Bearer <access_token>`. GET `/v1/users/me` возвращает профиль, GET `/v1/users/me/sessions` — активные сессии. DELETE `/v1/users/me/sessions` отзывает все свои сессии, DELETE `/v1/users/me/sessions/{session_id}` — одну свою. user_id всегда берётся из JWT. Данные профиля и IP не кешируются. Чужая и отсутствующая сессии дают одинаковый `404 session_not_found`. Отзыв запрещает refresh, но ранее выданные access JWT действуют до истечения срока.

## Кошельки

Для активного пользователя доступны POST `/v1/wallets` (создание, `201`), PATCH `/v1/wallets/{wallet_id}` (переименование, `204`) и POST `/v1/wallets/{wallet_id}/close` (закрытие, `204`). Требуется Bearer access JWT. Владельца задаёт JWT; имя содержит 1–64 символа после trim, валюта по умолчанию USD. Чужой кошелёк возвращает `404 wallet_not_found`. Закрытие с ненулевым балансом даёт `409 wallet_balance_not_zero`, переименование закрытого — `409 wallet_closed`. Контролируемая ошибка учётного состояния возвращает JSON `500 wallet_accounting_state_error`; остальные непредвиденные ошибки по-прежнему могут возвращать текстовый 500. Чтение доступно через GET /v1/wallets и GET /v1/wallets/{wallet_id}; история и новые финансовые операции также опубликованы.


Финансовые маршруты: POST/GET /v1/transfers, GET /v1/transfers/{transfer_id}, POST /v1/sandbox/top-ups, GET /v1/wallets/{wallet_id}/balance и /transactions, GET /v1/users/me/balances и /transactions. Sandbox выключен по умолчанию; нужен серверный оператор. Новые денежные ответы используют строки minor units; прежний WalletResponse сохраняет числовой balance_minor.
